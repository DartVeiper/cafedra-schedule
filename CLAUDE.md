## Кто пользователь и как с ним общаться

Методист кафедры, не программист. Пишет по-русски, неформально, иногда
с опечатками. Разбирается в git на базовом уровне (путал коммит/пуш/PR/
merge в начале работы) — объясняй просто, не сыпь жаргоном без пояснения.
Просил один раз: "делай сразу в мейн, если всё будет правильно" — то есть
по умолчанию коммить и пушить прямо в `main` без Pull Request'ов, если
явно не попросит иначе (один раз случайно открыл PR кнопкой на GitHub,
не поняв, что это — после объяснений смёржил его сам).

## Что это за проект

Локальное веб-приложение (FastAPI) для методиста кафедры: загружает файлы
расписания (индивидуальные занятия .xls/.xlsx + групповые .doc/.docx),
сводит в единую базу и ищет накладки (преподаватель/аудитория/студент в
двух местах одновременно). Работает как обычный сайт (localhost:8000) или
как собранный PyInstaller `.exe` — методисту не нужен Python/git.
Подробности архитектуры — в `README.md`, он поддерживается в актуальном
состоянии, читай его тоже.

## Правила работы в этом репозитории

- Весь код, комментарии, UI, коммит-сообщения — на русском.
- Коммитить и пушить сразу в `main`, без промежуточных веток/PR, если
  пользователь явно не попросит иначе.
- **Перед пушем всегда**: прогнать тесты (`cd backend && <venv>/bin/python -m pytest tests/ -v`)
  и, если менялся UI/поведение — поднять сервер и проверить вживую в
  браузере (в этой среде уже есть Chromium — `/opt/pw-browsers/chromium-*/chrome-linux/chrome`,
  Playwright ставится через pip). Скриншоты того, что получилось,
  отправлять пользователю через SendUserFile — он это ценит и просит
  сам, когда забываешь.
- После ручной проверки — обязательно убрать тестовые данные
  (`data/`, `config/` в корне репозитория при разработке из исходников)
  перед коммитом, чтобы не закоммитить мусор случайно.
- Тест `tests/test_pipeline_errors.py::test_corrupt_legacy_doc_is_skipped_not_crashed` зависит от
  окружения: если нет ни MS Word, ни LibreOffice (линукс-песочница, GitHub Actions), битый `.doc`
  попадает в `failed_files`; если конвертер есть — в предупреждения парсера. Тест проверяет оба
  исхода, поэтому теперь проходит везде (раньше падал вне машины с Word и ловился на CI).
- **Релиз** (`APP_VERSION`, запись в `app/changelog.py`, сборка `.exe`, GitHub Release
  `vX.Y.Z` с прикреплённым `.exe`) — делать ТОЛЬКО по явной просьбе пользователя
  («выпускай»). Если сессия идёт на его Windows-машине (`.venv\\Scripts` есть,
  `gh auth status` — залогинен как DartVeiper), Claude может сделать это сам, так
  было с v0.3.0: (1) тесты, включая `test_self_update_e2e.py`; (2) поднять версию +
  changelog; (3) коммит и `git push origin main`; (4) чистая сборка той же командой, что
  в `build_exe.bat` (сам bat заканчивается `pause` — запускать PyInstaller напрямую:
  `python -m PyInstaller --noconfirm --name CafedraSchedule --onefile
  --add-data "app/templates;app/templates" --add-data "app/static;app/static" desktop_app.py`);
  (5) запуск собранного .exe в песочнице (`LOCALAPPDATA` во временную папку, чтобы не
  трогать данные пользователя; `BROWSER="cmd /c exit"`, чтобы не открывался браузер) и
  прогон по реальным файлам; (6) `gh release create vX.Y.Z backend/dist/CafedraSchedule.exe
  --target main --title vX.Y.Z --notes-file ...` — текст в стиле прошлых релизов («Что
  нового с vA:», пункты, «Если у вас версия 0.3.0+ — обновитесь из приложения; 0.2.0 и старше —
  один раз вручную»); (7) проверка: скачать ассет по настоящей ссылке и сверить sha256 и размер,
  убедиться, что `update_check` из старой версии видит релиз. Без прямой просьбы —
  только поднять `APP_VERSION` и запушить, сборку и публикацию объяснить шагами.
  Не оставлять фоновых процессов/окон после тестов (проверить список процессов).

## Технические детали, которые легко забыть

- **Расположение данных зависит от режима.** При разработке из исходников
  (`is_frozen() == False`) `data/` и `config/` лежат в **корне репозитория**
  (`cafedra-schedule/data`, `cafedra-schedule/config`), НЕ в `backend/` —
  легко ошибиться и чистить не ту папку (уже наступали на эти грабли).
  В собранном `.exe` — `%LOCALAPPDATA%\CafedraSchedule\` (не рядом с
  `.exe`!), с автопереносом старых данных при первом запуске новой версии
  (`app/paths.py:migrate_legacy_storage`).
- `config/cabinets.json` (реестр кабинетов) хранится ОТДЕЛЬНО от `data/`
  намеренно — переживает удаление истории проверок.
- `Lesson` — dataclass с `eq=True`, поэтому **нехэшируемый** (`__hash__`
  автоматически `None`). Нельзя класть его в `set()`/использовать как ключ
  словаря — сравнивай через `==`/`is` напрямую, не через множества.

## Самообновление и «Что нового» — правила (важно, не ломать)

- **Любое изменение `app/self_update.py`, `app/update_check.py`, `build_exe.bat`
  проверять сквозным тестом на Windows:**
  `cd backend && ..\.venv\Scripts\python.exe -m pytest tests/test_self_update_e2e.py -v`
  (~20 с, настоящий cmd, занятый файл, битая загрузка). Он уже ловил две
  настоящие ошибки: (1) `find` в `.bat` мог оказаться утилитой из Git, а не
  системной — теперь `tasklist/find/ping` вызываются по полному пути
  `%SystemRoot%\System32\...`; (2) помощник запускался с `DETACHED_PROCESS`, и в
  нём `ping`/`chcp`/`tasklist|find` зависали — теперь `CREATE_NO_WINDOW`.
  Паузы в `.bat` — только через `ping`, не `timeout` (без консоли он не ждёт).
- **Сквозной тест на НАСТОЯЩЕЙ собранной программе:** `tests/test_self_update_frozen_e2e.py` +
  `tests/frozen_updater_probe.py` — собирает PyInstaller-onefile пробник (~1 мин), настоящим
  `start_update` обновляет его по HTTP и ждёт, что новая копия реально запустилась. Идёт в CI на
  Windows и в `release.yml` перед публикацией. Нужен потому, что подставные `whoami/hostname` из
  `test_self_update_e2e.py` не ловят особенности onefile (два процесса, своя temp-папка на запуск,
  наследование `_PYI_*`). Он поймал третью настоящую ошибку: после подмены новая копия **падала при
  старте молча** (наследовала переменные PyInstaller и считала себя дочерним процессом закрывшейся
  старой) — лечится `self_update.independent_launch_env()` (`PYINSTALLER_RESET_ENVIRONMENT=1`).
  Если меняешь способ запуска/перезапуска программы — этот тест надо гонять и он должен остаться зелёным.
- **Диагностика по жалобам методиста.** Чёрная консоль с заголовком `find "<число>"`, «ничего не
  происходит» = на компьютере версия ≤ 0.2.x (там помощник шёл с `DETACHED_PROCESS` и голым `find`);
  это баг УСТАНОВЛЕННОЙ старой версии, обновлением кнопкой не лечится — только один раз заменить
  `.exe` вручную (скачать с GitHub Releases поверх старого, удалить рядом `CafedraSchedule.exe.new` и
  `_cafedra_update.bat`; данные в `%LOCALAPPDATA%` не пострадают). Версии 0.3.0–0.3.5 по кнопке подменяют
  файл, но новая копия сама не стартует (баг выше) — достаточно запустить программу вручную. Исправлено
  в `main` после 0.3.5, попадёт в следующий релиз; после него кнопка работает целиком.
- Подмена .exe: старый → `.bak`, новый на его место, при сбое откат; повторы до
  30 с (файл бывает занят после выхода — загрузчик PyInstaller, антивирус).
  Скачанный файл проверяется (Content-Length, размер ассета GitHub, заголовок `MZ`).
- **Перед релизом** — запись для новой версии в `app/changelog.py` (человеческим
  языком, для методиста: показывается по кнопке «Что нового» в шапке и один раз
  сама открывается после обновления) + `APP_VERSION`. Тест
  `tests/test_changelog.py` упадёт, если записи для текущей версии нет. Текст
  релиза на GitHub (его пишет автор) показывается в баннере обновления и в окне
  «Что нового» — через `app/mdlite.py` (HTML экранируется).
- Превью баннера обновления: подставить `update_check._cache["result"]` и
  `m.check_for_update` / `m.self_update.can_self_update` (см. идею в истории сессии:
  отдельный uvicorn на 8001) — на настоящий GitHub для этого ходить не нужно.

## Сетка времени (по дням) и кураторский час

- Сетка времени начала занятий РАЗНАЯ по дням (понедельник сдвигается из-за
  кураторского часа, суббота — свой короткий день) и меняется каждое полугодие
  (кураторский час может переехать на другой день). Поэтому `app/timegrid.py`
  восстанавливает сетку из данных по каждому дню отдельно, а подписи дней
  («Кураторский час в 14:25 — время сдвинуто») берутся из служебных слотов
  групповых файлов (`notes["special_slots"]` в импорте). Ничего про конкретные
  дни в коде не зашито — не зашивать.
- Время не из сетки своего дня = «нестандартное» (вероятная опечатка), показывается в
  отчёте, в списке кабинетов (⚠) и в сетке кабинета. Если за день < 20 занятий
  (загружен один файл) — сетку не определяем и ничего не помечаем.
- Сетка кабинета: строки = порядковый номер занятия в дне, время — в ячейке.

## Раскладка по кабинетам в Word/Excel и страница установки обновления (0.3.6, в разработке)

- `layout_export.py` — «Раскладка по кабинетам» целиком (`/report/{id}/layout.docx` и `.xlsx`), формат взят с
  ручной раскладки кафедры (фото таблицы «КАФЕДРА ФОРТЕПИАНО 2026-2027 учебный год 1семестр»): на каждый день таблица,
  строки = слоты сетки ЭТОГО дня (+ кураторский час серой строкой), столбцы = кабинеты кафедры из реестра (если реестр
  пуст — все кабинеты индивидуальных занятий, `cabinets.layout_rooms`), в ячейке преподаватель / студент · группа /
  предмет / «Концертмейстер (концертмейстер)» — преподаватель и концертмейстер одного студента сливаются в одну запись;
  групповая пара — «ПАРА 92Ф…» и «↑ пара продолжается» во втором слоте; накладка — красная ячейка. В Excel ещё лист
  «Все занятия» (плоский список с автофильтром). Формат 3 как ВХОД по-прежнему не парсим — но ВЫВОД в этом виде теперь есть.
- `update_progress.html` + `/api/version`: после «Скачать и установить» страница опрашивает сервер: упал → поднялся с новой
  версией → «Готово», вернулась старая → понятное сообщение; не закрылся за 30 с / не поднялся за 3 мин → инструкция
  ручной установки со ссылкой на релиз. В баннере на главной всегда есть «Скачать вручную».
- ВАЖНО про старые установки: у версий **0.2.0 и старше** (до исправления в 0.3.0) помощник обновления зависает —
  чёрное окно `find "<PID>"` и ничего не происходит (скриншот от методиста, октябрь 2026). Исправить это нельзя: скрипт
  зашит в их установленный .exe. Им нужно ОДИН раз скачать свежий .exe с GitHub вручную; дальше самообновление работает.
  Зависшие `cmd/find` после неудачи нужно закрыть (крестиком или диспетчер задач), рядом с .exe могут остаться
  `CafedraSchedule.exe.new` и `_cafedra_update.bat` — их можно удалить.

   не строй UI выбора кафедры без явной просьбы).
4. **Очистка старых загрузок + удаление проверки + экспорт в Word + даты
   по-человечески** — сырые файлы больше не копятся вечно в `data/uploads/`,
   есть кнопка "Удалить эту проверку", кнопка "Скачать отчёт в Word"
   (`python-docx`, уже в зависимостях), даты в "Недавние проверки" в
   локальном времени и читаемом формате.
5. **Фильтр отчёта по ФИО** — выпадающий список (не текстовый поиск!)
   "Показать только по ФИО" на странице отчёта, точное совпадение (не
   подстрока — выбор всегда из готового списка). "Всё в порядке", если
   у выбранного человека накладок нет.
6. **Самообновление `.exe`** — кнопка "Скачать и установить" в баннере на
   главной, скачивает новый `.exe` и подменяет себя на месте (bat-хелпер
   ждёт завершения процесса, см. `app/self_update.py`). Работает только
   для frozen `.exe` на Windows.

## Открытые вопросы / сознательно не сделано

Не берись за эти пункты без явного запроса — они требуют вводных от
пользователя, которых пока нет:

- **Формат 3** (мастер-раскладка по аудиториям) — РЕШЕНО НЕ ПАРСИТЬ, и это
  окончательно, не поднимай вопрос заново без новых вводных. Получили
  реальный образец (`data/samples/raw/Раскладка ... .docx`, 89×15, одна
  таблица), сверили вручную: для кабинетов 415 и 405 по понедельнику наши
  данные (Форматы 1+2, через `cabinets.build_room_schedule`) совпали с
  мастер-раскладкой 1-в-1 (26/26 занятий, только методист местами лениво
  не дописывал повторяющегося студента от руки — у нас как раз точнее).
  Ячейки там — вперемешку текст без разделителя (препод+студент+предмет,
  иногда "(концертмейстер)" прямо в строке), набор колонок-кабинетов
  меняется по дням — парсить это надёжно дороже, чем оно того стоит, когда
  те же данные уже есть чище через Формат 1+2. Вкладка "Кабинеты" — прямая
  замена: не нужно объяснять методисту, что это что-то новое, а не старый
  Формат 3, который он раньше собирал руками. Разница в "наборе колонок по
  дням" у Формата 3 — это экономия места на бумаге, не потеря информации:
  у нас кабинет — отдельная страница на все 6 дней, пустой день просто
  показывает свободные ячейки, ничего скрывать не требуется.
- **Ростер подгрупп** — нет данных о составе подгрупп ни в одном формате,
  накладки "студент × подгруппа" всегда помечаются "требует проверки".
  Нужно решить, как методист будет передавать состав (отдельный файл?
  вручную в интерфейсе?).
- **Сопоставление людей по ФИО без уникального ID** — риск ложной накладки
  у тёзок с одинаковыми инициалами. Один конкретный подслучай (учёное
  звание-приставка у преподавателя) уже нашёлся на практике и починен
  (см. пункт 0 выше). Остальное — опечатки в ФИО студента между файлами
  (уже частично сглажено нечётким сравнением в `conflicts.py`, см.
  `_names_similar`) и дуэты/ансамбли, записанные одним полем ("Захарова,
  Кузнецов") — эти попадают в выпадающий список "Показать по ФИО" как
  отдельные мусорные пункты. Пока не подтверждённая на практике проблема
  именно для конфликт-детекшна (спрашивали — реальных ложных накладок от
  этого не было), не чинить вслепую без нового конкретного примера.
- **Несколько кафедр** — `cabinets.py` уже хранит данные в форме
  `departments`, но UI переключения между кафедрами не строился (нужна
  вторая реальная кафедра, чтобы понимать, что там за кабинеты и как
  переключаться).
